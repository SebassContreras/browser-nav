# 042 — custom-form-controls-and-bidi-actionability

## Goal
Enable reliable automation of modern customized form controls and client-side URL routing over WebDriver BiDi: `browser-nav` must allow actionability and clicking on visually-hidden native `<input type="checkbox">` and `<input type="radio">` through their associated visible `<label>`, support declarative option selection for `<select>` tags in `browser_fill`, and tolerate client-side query-string rewriting in `assertFresh` / `sameDocumentUrl`. Verified by unit tests and end-to-end integration tests.

## Requirements
- R1: Visually-hidden checkbox and radio button actionability: when an `<input type="checkbox">` or `<input type="radio">` has zero dimensions (`width === 0 || height === 0`) or is visually clipped/hidden (e.g. `class="visually-hidden"`), `checkActionable` and `locate` inspect its associated `<label>` (via `el.labels`, wrapping `<label>`, or `label[for="..."]`). If the label is visible and unobstructed, actionability passes and clicking targets the label. Partitions: (a) checkbox with wrapping `<label>`, (b) checkbox with `label[for]`, (c) visible native checkbox, (d) radio button with associated label, (e) hidden input with detached/missing label, (f) hidden input with disabled or covered label. Invariants: a truly invisible/detached control with no visible label is rejected with `PwaNavError("not_actionable")` (`element is not visible` or `element is covered`); clicking the label toggles checkbox state or activates the radio button.
- R2: Declarative option selection on `<select>` elements in `prepareFill` / `fill`: `browser_fill` supports `<select>` elements by matching the input text against option labels and values (exact label match, exact value match, and case-insensitive substring fallback), setting `select.value`, and dispatching standard `change` and `input` events. Partitions: (a) text exactly matches option label, (b) text exactly matches option value, (c) text matches label or value via case-insensitive substring, (d) text matches no option, (e) disabled `<select>` element. Invariants: `<select>` is supported by `fill` rather than rejected as unsupported; an unmatchable option value fails with `PwaNavError("not_actionable")` with an actionable recovery hint; readback verifies the selected option text or value.
- R3: Resilient URL matching in `sameDocumentUrl`: `sameDocumentUrl` tolerates URL query-string parameter additions, deletions, and ordering changes when the origin and pathname are identical (e.g. SPA client-side tracking parameters). Partitions: (a) query params stripped by SPA router, (b) query params added by SPA router, (c) query params reordered, (d) pathname changes, (e) origin changes, (f) malformed or empty URLs (`""`, invalid URI strings). Invariants: returns a boolean contract without throwing; genuine page navigations to different routes still cause `assertFresh` to raise `StaleRefError`; SPA tracking query changes do not invalidate live element references; malformed URLs return `false`.

## Design
- D1 (R1): In `src/browser/actions.ts:checkActionable`, if `el.localName === "input"` and `type` is `"checkbox"` or `"radio"`, look up its associated label (`(el as HTMLInputElement).labels?.[0] || el.closest("label") || (el.id ? el.ownerDocument.querySelector('label[for="' + el.id + '"]') : null)`). If the input is not directly visible but the label is visible, evaluate actionability against the label. In `LOCATE_NODE_SOURCE`, return the label when the input is styled hidden so BiDi pointer actions target the visible click target. Sources: WHATWG HTML Living Standard, §4.10.4 "The label element" https://html.spec.whatwg.org/multipage/forms.html#the-label-element (accessed 2026-11-03); W3C WebDriver BiDi Specification, §3.5 "Input actions" https://w3c.github.io/webdriver-bidi/ (accessed 2026-11-03); W3C WebDriver 2, §11.1 "Element Interactability" https://www.w3.org/TR/webdriver2/#element-interactability (accessed 2026-11-03).
- D2 (R2): In `src/browser/actions.ts:prepareFill`, remove the blanket rejection for `<select>`. For `tag === "select"`, verify the element is not disabled, focus it, and return `kind: "select"`. In `fillLocator`, when `prep.kind === "select"`, bypass keyboard key action generation (`buildFillKeyActions`) and execute an in-page option selection script that matches `text` against options (exact label, exact value, then case-insensitive substring), sets `select.value`, and dispatches bubbling `input` and `change` events. In `readBackMatches`, compare `text` against `(el as HTMLSelectElement).selectedOptions[0]?.text` or `.value`. Update the `fill` unsupported target error hint to mention select dropdowns. Sources: WHATWG HTML Living Standard, §4.10.7 "The select element" https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element (accessed 2026-11-03); W3C DOM Specification, §4.4 "Interface Event" https://dom.spec.whatwg.org/#interface-event (accessed 2026-11-03).
- D3 (R3): In `src/browser/locate.ts:sameDocumentUrl`, parse both URLs using `new URL(url)` within a `try/catch` block and compare `parsedA.origin === parsedB.origin && parsedA.pathname === parsedB.pathname`. If pathname and origin match, return `true`, ignoring fragment and query parameters. Malformed or unparseable URLs safely return `false`. Source: WHATWG URL Living Standard, §4.3 "URL class" https://url.spec.whatwg.org/#url-class (accessed 2026-11-03).

### Trade-offs & Mitigations
- **D1 (Label Delegation vs Forcing Direct Input Clicks):**
  - *Pros:* Matches actual human interaction in modern web frameworks (Tailwind, Artdeco, Material) where native inputs are hidden for custom styling.
  - *Cons:* If a label covers multiple inputs, ambiguity could arise.
  - *Mitigation:* Restrict lookup to `el.labels[0]`, explicit `for=id` match, or closest ancestor `label`.
- **D2 (JavaScript Value Setting & Event Dispatch vs Native Key Navigation for `<select>`):**
  - *Pros:* Native OS select menus cannot be driven via cross-platform BiDi mouse actions; setting `value` and dispatching `change`/`input` reliably triggers React/Vue/Angular state bindings.
  - *Cons:* Bypasses native keyboard arrow navigation.
  - *Mitigation:* Dispatch both `input` and `change` bubbling events to ensure complete DOM listener compatibility.
- **D3 (Origin + Pathname Equality vs Full URL Equality):**
  - *Pros:* Prevents spurious `StaleRefError` when SPAs rewrite tracking, referral, or state query parameters without changing the document or page layout.
  - *Cons:* Multi-view SPAs where different views are keyed purely by query parameters (e.g. `?tab=settings`) might be considered same document.
  - *Mitigation:* If the DOM actually mutates, role/name locator count checks in `assertFresh` catch element disappearance regardless.
